# Импорт и расчёт тренировок

## Загрузка и хранение

Спортсмен загружает исходный файл `.fit` в разделе «Тренировки». Результат содержит ссылку на карточку, статус импорта и предупреждение о похожей записи, если оно есть. Тренер читает тренировки команды и может повторно обработать исходный файл.

По умолчанию размер загрузки ограничен 32 МиБ. `CTM_FIT_MAX_BYTES` задаёт предел входного файла и распакованного FIT. Сервер проверяет расширение, объявленный размер, фактическую структуру FIT Activity и CRC. Декодирование ограничено семью сутками между началом и окончанием, 250 000 точек, 400 000 сообщений и 1 500 000 полей. Внутренний блочный контейнер `.ZIP` некоторых Magene/Geoid считается транспортной оболочкой FIT. ZIP-архивы общего назначения и цепочки из нескольких FIT в одной загрузке требуют извлечь отдельные файлы Activity. [Протокол FIT](https://developer.garmin.com/fit/articles/fit-protocol/fit_protocol.html) · [Структура Activity](https://developer.garmin.com/fit/file-types/activity) · [Описание контейнера CC600](https://gist.github.com/ehntoo/a8384a85c00a9d964325c7bec2665102)

- Оригиналы хранятся в `CTM_FIT_PATH` вне frontend, по умолчанию в `data/fit/<athlete_id>/<sha256>.fit`. Байты обычного FIT и контейнера сохраняются в исходном виде. Приложение выдаёт текущий оригинал через защищённый API. При переносе данных сохраняйте SQLite и весь каталог оригиналов.
- Повторный импорт по SHA‑256 в границах спортсмена возвращает прежнюю тренировку. Стандартный FIT и его блочная оболочка также объединяются по хешу распакованных байтов. Внешний ID хранится с атлетом и источником. Обновлённый файл с тем же внешним ID сохраняет ID тренировки и RPE, а прошлые оригиналы остаются в хранилище. Похожие по времени начала, длительности и дистанции файлы помечаются для проверки, объединение требует точного совпадения или общего внешнего ID.
- Оригинал публикуется атомарным переименованием перед фиксацией SQLite. Если процесс прерван между записью файла и фиксацией базы, оставшийся файл недоступен через API. При повторном импорте сервис проверяет его хеш и может использовать его снова.
- Временные ряды хранятся сжатыми блоками по 512 записей. Сохраняются исходный порядок записей, исходные поля и их единицы, дополнительные поля, значения датчиков и GPS. Для расчёта отдельно сортируются записи со временем. При одинаковом времени берётся последнее присутствующее значение каждого канала. В карточке показаны числовые сводки. API отдаёт ряд постранично.
- В сводке предпочтительны допустимые значения из FIT Session. Скорость хранится в м/с, дистанция и высота в метрах, температура в °C. При отсутствии итога среднее и максимум рассчитываются по записям с покрытием канала от 90% рабочего времени. Набор высоты берётся из FIT. Дистанция может быть взята из последнего монотонного счётчика дистанции около конца сессии. Время движения берётся из FIT либо считается по скорости выше 0,5 м/с при полном покрытии рабочего времени. Полное время, время таймера и время движения показываются отдельно.

## Алгоритм `fit-cycling-v1`

**Рабочее время.** Предпочтительны события таймера. Если итог таймера совпадает с длительностью сессии с точностью до одной секунды, используем её границы. Если события отсутствуют или противоречат итогу и сессия содержит паузы, рабочие интервалы можно восстановить по разрывам ряда. Сумма длин интервалов должна совпасть с итогом таймера с допуском 0,5% с нижней границей 2 с и верхней 15 с. Источник времени фиксируется. Если время восстановить невозможно, соответствующие расчёты остаются пустыми. [Официальное описание записей и событий таймера](https://developer.garmin.com/fit/articles/cookbook/encoding_activity_files.html)

**NP.** Измерения проецируются на секунды внутри рабочих интервалов. Предыдущее показание сохраняется до следующего замера на интервале до 2 с, более длинный разрыв сохраняется пропуском после измеренной секунды. Скользящее окно в 30 секунд не проходит через паузу или пропуск мощности. NP — корень четвёртой степени из среднего четвёртых степеней средних мощностей полных окон. Нужны как минимум одно полное окно, покрытие мощностью от 90% рабочего времени и от 80% возможных 30‑секундных окон. Измеренные 0 Вт учитываются. Отсутствующая мощность не превращается в нулевую. [Методика TrainingPeaks](https://www.trainingpeaks.com/coach-blog/normalized-power-how-coaches-use/)

**IF и TSS.** `IF = NP / FTP`, `TSS = (время таймера в часах) × IF² × 100`. FTP выбирается на дату начала в часовом поясе спортсмена. С тренировкой сохраняются значение FTP, дата его действия, часовой пояс, границы зон, версия алгоритма и пороги. Обычная повторная обработка использует сохранённые FTP и зоны. Чтобы взять актуальные значения из истории профиля, тренер явно выбирает обновление параметров. Операция фиксируется в аудите. [Формулы и определения TrainingPeaks](https://www.trainingpeaks.com/learn/articles/normalized-power-intensity-factor-training-stress/) · [Справка TrainingPeaks по NP и TSS](https://help.trainingpeaks.com/hc/en-us/articles/204071804-Normalized-Power)

**Зоны и RPE.** Время по зонам и распределение мощности суммируются только по рабочим секундам с показаниями. Неизвестное время и время вне зон выводятся отдельно. Верхняя граница зоны исключается. Распределение мощности использует интервалы по 50 Вт. Нагрузка RPE равна оценке × минуты таймера FIT Session. При отсутствии времени таймера оценка сохраняется, нагрузка остаётся пустой.

## API и проверка совместимости

- `POST /api/v1/workouts/import` принимает `application/octet-stream` и имя файла в заголовке `X-FIT-Filename` в URL-кодировке. Успешный ответ возвращает `workout_id`, `status` и `potential_duplicates`.
- `GET /api/v1/athletes/{athlete_id}/workouts` возвращает историю. Карточка доступна по `/api/v1/workouts/{id}`, ряд, метрики, исходный файл и оценка — по суффиксам `/samples`, `/metrics`, `/fit` и `/rpe`. Для ряда можно передать `offset`, `limit` и `include_fields=true`.
- `POST /api/v1/workouts/{id}/reprocess` доступен тренеру. Параметр `refresh_parameters` по умолчанию равен `false`. Импортер для источников использует единый `WorkoutImportService.import_fit`. Интеграция с OnelapFit запланирована на этап D.
- В автоматических тестах используются синтетические FIT Activity с известными результатами. Проверены оба размера заголовка, big-endian, сжатые метки времени, резервный бит заголовка записи, блочный контейнер Magene, интервалы и пропуски мощности, поездки без мощности, повреждённые FIT и повторные загрузки.
- Дополнительно локально прочитаны реальные Geoid CC600 и Garmin Edge 500, а также три файла SDK Garmin с дополнительными полями, пульсом и переключениями передач. Данные сторонних тренировок в репозитории не хранятся. Проверка охватывает имеющиеся образцы и не подтверждает все модели или прошивки.
