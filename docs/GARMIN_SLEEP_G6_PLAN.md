# G6.1. Аудит Garmin Sleep и план интеграции

Проверено 22 ноября 2026 года. Garmin Connect Personal API официально предоставляет данные сна владельца ключа. Для Cycling Team Monitor допустимый кандидат на первый пилот — отдельный локальный экземпляр для одного владельца, с доступом только для него и после сверки принятых им условий. Для командного импорта и показа данных тренеру нужен отдельный подтверждённый доступ Garmin Connect Developer Program. [Garmin Personal API FAQ](https://developer.garmin.com/gc-developer-program/personal/personal-faq) · [Обзор вариантов доступа Garmin](https://developer.garmin.com/gc-developer-program/overview/)

**Один аккаунт.** Предлагаемый пилот использует одно привязанное к владельцу подключение, отдельную БД экземпляра и серверную настройку через скрытый ввод в локальной консоли. Данные доступны только владельцу. Общая рабочая БД и тренерские экраны команды в таком пилоте исключены. Владельцу достаточно предоставить для сверки текст условий без ключа, токена, снимков данных или доступа к аккаунту.

**Команда.** Garmin предлагает Health API в Business Starter и Enterprise. Starter использует push, ограничивает число пользователей и не включает исторические данные. Enterprise предлагает push или ping/pull и расширенную историю. Для каждого спортсмена требуется отдельное согласие в Garmin и привязка Garmin User ID к его учётной записи CTM. Официальный поток использует OAuth 2.0 Authorization Code с PKCE. Перед командной реализацией нужны одобрение приложения, подтверждение тарифа, схемы сна, условий тренерского доступа, отзыва и хранения, а также согласованный способ приёма данных по HTTPS. Сбор нескольких Personal API keys в общий экземпляр в план не входит. [Возможности Starter и Enterprise](https://developer.garmin.com/gc-developer-program/overview/) · [Health API](https://developer.garmin.com/gc-developer-program/enterprise/health-api/) · [OAuth 2.0 PKCE Garmin](https://developerportal.garmin.com/sites/default/files/OAuth2PKCE_1.pdf)

## 2. Поля сна Personal API

В публичной спецификации OpenAPI 1.0.0 однодневный запрос `GET /sleep-service/sleep/dailySleep?date=YYYY-MM-DD` документирован с ответом `DailySleepDTO`. `GET /sleep-service/sleep/dailySleepSummariesByDate` с `startDate` и `endDate` возвращает массив таких сводок. Структуру фактического ответа, представление меток времени и поведение при пустой ночи нужно сверить на отдельно разрешённом пилоте. В схеме `DailySleepDTO` поля не объявлены обязательными. [OpenAPI Personal](https://developer.garmin.com/gc-developer-program/personal/swagger-docs/) · [Реализация запросов в клиенте Garmin](https://github.com/garmin/connect-personal-api-python/blob/main/src/garmin_personal_api/client.py#L116-L131)

| Показатель | Подтверждённое поле и использование в CTM |
| --- | --- |
| Дата и идентификатор | `calendarDate` — календарная дата Garmin, `id` — ID исходной записи при наличии. Храним отдельно от даты дневника. |
| Начало, конец и смещение | `sleepStartTimestampGMT` / `sleepEndTimestampGMT` — границы окна сна в UTC. Локальные аналоги `sleepStartTimestampLocal` / `sleepEndTimestampLocal` помогают сохранить исходные смещения при однозначном формате. Схема помечает метки как `date-time`, а в описании упоминает миллисекунды. Формат фактического ответа проверяется перед включением импорта. |
| Продолжительность | `sleepTimeSeconds` — измеренный ночной сон без дневного сна. Храним секунды, для G2–G5 приводим к целым минутам единым правилом ближайшей минуты (30 секунд округляются вверх). Время между границами у Garmin — окно сна, которое может включать бодрствование. |
| Фазы и бодрствование | `deepSleepSeconds`, `lightSleepSeconds`, `remSleepSeconds`, `awakeSleepSeconds`. Нулевое наблюдение и отсутствующее поле различаются. |
| Оценка Garmin | В `sleepScores` документированы компоненты `SleepScoreItem.value` со шкалой 0–100. Ключ итогового компонента надо подтвердить по фактическому контракту. До подтверждения итоговый балл остаётся пустым. |
| Пульс, HRV и другие данные | `DailySleepDTO` содержит `avgHeartRate`. Ночной HRV (`lastNightAvg`, `lastNight5MinHigh`) предусмотрен в отдельной сводке HRV. Дневной пульс и пульс покоя также имеют отдельный API. В схеме сна есть дыхание, SpO₂ и другие поля. Первая версия может отображать ночной пульс, когда его наличие и единица подтверждены, остальные дополнительные метрики включать по отдельному согласованию и при надёжной привязке к той же ночи. |

Данные зависят от устройства, полноты ночи и загрузки в Garmin Connect. Пропуски сохраняются как `null`. При отсутствии обязательной для G6 даты, согласованных границ или измеренной длительности запись помечается в журнале ограниченным кодом диагностики и не участвует в аналитике до получения полной сводки. Фазы, дневной сон и время бодрствования сохраняются только в предусмотренных полях и никогда не прибавляются к ночной продолжительности. Оценка Garmin отображается с её шкалой как показатель устройства. Субъективное качество сна и самооценка восстановления остаются самостоятельными показателями дневника. [OpenAPI Personal](https://developer.garmin.com/gc-developer-program/personal/swagger-docs/) · [FAQ Garmin о покрытии устройств](https://developer.garmin.com/gc-developer-program/enterprise/program-faq/)

## 4. Предлагаемые архитектура и схема хранения

- **FastAPI.** Ввести сервис нормализации сна и разрешения источников. Персональный адаптер получает сводки через фиксированные официальные HTTPS-адреса и отдаёт нормализованные наблюдения. Будущий Business-адаптер будет принимать подтверждённые события Health API с другим механизмом авторизации, сохраняя тот же интерфейс импорта. Использовать имеющийся `httpx` и явное управление токеном. Официальный SDK служит контрольным примером запросов, его файловый кэш содержит токены открытым текстом. [Клиент Garmin и кэш](https://github.com/garmin/connect-personal-api-python#bearer-token-cache) · [Зависимости проекта](../backend/requirements.txt)
- **`sleep_days`.** Одна логическая ночь на `(athlete_id, sleep_date)`. Хранить IANA-пояс привязки, текущий ручной или исторический вариант, ссылку на актуальную сводку Garmin, выбор источника и версию для конкурентных изменений. Ручной вариант содержит начало и конец со смещениями (если указаны), введённую или рассчитанную длительность, время и способ правки. Для каждой отображаемой метрики API отдаёт значение и происхождение (`manual`, `garmin`, `legacy` при неподтверждённом происхождении). Для отсутствующего значения источник пуст.
- **`garmin_sleep_observations`.** Хранить нормализованные версии сводки с датой Garmin, ID исходной записи, UTC-границами, исходными смещениями при наличии, длительностью, согласованными необязательными полями и временем получения. Хранить идентификатор подключения к источнику и привязку к логической ночи. Уникальность исходной записи проверять в пределах спортсмена и подтверждённой привязки Garmin. Версии создавать при изменениях полей. Исходная версия, которую спортсмен исправил или сравнил, сохраняется в пределах применимых условий. Полный ответ Garmin, произвольные заметки и ненужные идентификаторы в SQLite не сохраняются.
- **`garmin_connections` и `garmin_sync_runs`.** Подключение хранит режим, поколение привязки, безопасную ссылку на секрет, статус, последнюю попытку, последнее успешное получение, курсор проверенного диапазона и срок следующей допустимой попытки. Журнал содержит интервал, время и исход задачи, числа добавленных, обновлённых и пропущенных записей и нормализованный код ошибки. Обновление записей и продвижение курсора происходят в одной транзакции на успешно обработанный диапазон. В отчётах и журналах остаётся служебная статистика без полезной нагрузки и секретов.
- **Отключение.** Удалить учётные данные, очистить токен в памяти и увеличить поколение подключения, чтобы уже начатая задача не записала результат. Обычное отключение сохраняет записи сна в рамках применимых условий. Удаление самих данных и запрос на отзыв обрабатываются по отдельным правилам хранения. Для Personal отзыв у Garmin выполняет владелец ключа. Для Business планируется официальный endpoint снятия регистрации и обработка уведомлений об отзыве. [Отзыв ключа Personal](https://developer.garmin.com/gc-developer-program/personal/personal-faq) · [Отзыв Business](https://developerportal.garmin.com/sites/default/files/OAuth2PKCE_1.pdf)

### Защита секретов

Для локального пилота предлагается хранить персональный ключ под Windows DPAPI в контексте отдельной серверной учётной записи. Зашифрованный файл или запись хранилища размещаются вне каталога проекта с доступом только серверной учётной записи, а SQLite содержит ссылку. Настройка выполняется локальной командой со скрытым вводом, без секрета в аргументах, `.env`, истории оболочки или браузере. Access token держится в памяти. Отключение удаляет и ключ из хранилища, и токен из памяти. Копия или восстановление БД не должны восстанавливать действующее подключение или получать доступ к старой ссылке.

Для будущего ввода через браузер потребуется HTTPS на проверенном origin и проверка схемы сервером с учётом только доверенного reverse proxy. Одних заголовков от клиента недостаточно. У существующего локального HTTP предусмотрены просмотр статуса и ручной дневник без формы для реального ключа. Для Business OAuth callback связывается с текущей сессией спортсмена через одноразовый `state` и PKCE. Долгоживущие токены хранятся в защищённом серверном хранилище или шифруются отдельным ключом вне SQLite. Секреты не попадают в URL, хранилища браузера, API-ответы, логи, телеметрию и PWA-кэш. Запросы Garmin идут с проверкой TLS, без переадресации заголовков авторизации на другой хост. [Текущая защита API](../backend/app/main.py) · [Параметры Windows-сервера](../backend/app/windows_server.py)

### Синхронизация и восстановление после сбоя

- Разрешённое подключение ставит первую задачу. Кнопка спортсмена добавляет или переиспользует задачу в той же очереди. По расписанию используется тот же путь. В Personal частоту, максимальную глубину догрузки и расписание определяют после подтверждения условий и лимитов. Один запрос сводки охватывает не более 31 дня, включая дополнительный запас на расхождение дат Garmin и CTM. После включения ноутбука очередь продолжает обработку от сохранённого курсора. Перекрытие недавнего окна позволяет учесть записи, поздно загруженные или исправленные в Garmin. Старые промежутки вне разрешённой глубины остаются пропусками.
- Один исполнитель на экземпляр хранилища и одна активная задача на подключение. В SQLite использовать атомарный захват задачи с ограниченным временем аренды и поколением подключения. Сеть вызывать вне транзакции записи. После перезапуска просроченная задача возвращается в очередь или завершается по лимиту попыток. Повтор после частичного сбоя идемпотентен, курсор продвигается только после сохранения диапазона.
- Переиспользовать access token до истечения. При ответе, указывающем на недействительный токен, допустим один новый обмен и один повтор исходного запроса. Подтверждённую ошибку авторизации остановить до повторной настройки. При сетевом сбое, `5xx` или `429` использовать ограниченное число повторов с задержкой и `Retry-After`, если заголовок пришёл. И ручные, и фоновые задачи соблюдают единый предел запросов, включая обмен токена. Отдельно показывать отсутствие данных, недоступную возможность и временную ошибку сервиса.

## 5. Привязка ночи и выбор источника

1. **Дата сна — дата пробуждения** в IANA-поясе профиля спортсмена. Например, сон с 23:15 до 07:00 относится к дате 07:00. При первом импорте дату определяем по подтверждённому UTC-времени окончания и поясу, действующему в профиле при привязке. Сохраняем пояс вместе с датой, отдельно от даты и смещений Garmin. Повторный импорт по тому же ID сохраняет привязку, даже если пояс профиля изменился. Если коррекция Garmin переносит дату в сохранённом поясе, спорное изменение требует явного подтверждения спортсменом. Ручной перенос даты атомарно обновляет указатель на ночь и обе даты аналитики, существующая запись на целевой дате вызывает конфликт.
2. **Ручной ввод.** Спортсмен может указать дату пробуждения, время начала и конца, длительность и при необходимости заполнить поля обычной анкеты. Время начала позже времени конца означает начало накануне. При двух метках сервер считает разницу между моментами в UTC с учётом их смещений, интерфейс показывает расчёт и позволяет его исправить. При переводе часов двусмысленное время требует выбора смещения, несуществующее время требует исправить ввод. Допускается длительность без границ, как в текущем дневнике. Субъективное качество сна, восстановление, усталость, настроение, болезненность и статус тренировочного дня записываются в прежней анкете.
3. **Приоритет по умолчанию.** Существующее ручное или историческое значение длительности сохраняется и участвует в расчёте. При его отсутствии используется корректное значение Garmin. При расхождении интерфейс показывает оба значения, метки источников и время синхронизации. Спортсмен выбирает, какое значение использовать. Согласованные границы ночи показываются вместе с их источником. Фазы, оценка и пульс Garmin остаются в своей сводке даже при выбранной ручной длительности.
4. **Правка и повтор.** Ручная правка создаёт или обновляет ручной вариант и делает его выбранным, сохраняя сравниваемую версию Garmin. Повторный импорт обновляет вариант Garmin и сохраняет ручной выбор. Явный выбор Garmin использует его актуальную подтверждённую сводку, сохраняя доступный ручной вариант. Разрешение конфликта проверяет версию ночи, чтобы выбор не применился молча к изменившимся данным.
5. **Дедупликация.** Сначала сопоставляется подтверждённая исходная привязка и ID. При отсутствии ID повтор сопоставляется по дате Garmin и границам UTC в рамках той же привязки. Изменившиеся границы без ID требуют однозначного сопоставления с существующей ночью. Если данных для него недостаточно или за один день пришло несколько конкурирующих сводок, сохраняется доступный выбор и состояние конфликта. В аналитике за одну календарную дату учитывается одна продолжительность. Пустой ответ и временная ошибка сохраняют ранее полученные данные.

## 6. Контракт API, интерфейс и аналитика

| Предлагаемый маршрут под `/api/v1` | Доступ и назначение |
| --- | --- |

Тренеру доступно чтение разрешённых показателей и источника по существующему `AthleteScope`, с учётом режима интеграции и согласия. Запрос истории ограничивается диапазоном и размером страницы. |
| `PUT /athletes/{id}/sleep/{date}/manual` | Спортсмен обновляет собственные границы или длительность, включая очистку ручного варианта. Новый маршрут поддерживает сон без анкеты. |
| `PUT /athletes/{id}/sleep/{date}/selection` | Спортсмен меняет выбранный источник с проверкой версии. |
| `GET /athletes/{id}/garmin` | Спортсмен видит статус, последнюю успешную синхронизацию и действия для восстановления. Тренер получает только время последней успешной синхронизации разрешённого командного подключения в карточке. |
| `POST /athletes/{id}/garmin/sync`, `DELETE /athletes/{id}/garmin` | Спортсмен запускает задачу или отключает своё подключение. Изменяющие маршруты используют действующие проверки сессии, Origin и CSRF. Реальное подключение Personal в пилоте настраивается через серверную команду. Маршруты начала авторизации и callback появятся при одобрении Business. |

- В профиле спортсмена добавить «Подключение Garmin» с состояниями «Не подключено», «Подключено», «Синхронизация выполняется», «Последняя синхронизация успешна», «Ошибка авторизации», «Временная ошибка синхронизации», «Требуется повторное подключение» и «Функция недоступна для данного типа API». Показывать дату последнего успеха, кнопку синхронизации только при доступном подключении и действие отключения. До получения рабочего доступа интерфейс показывает фактическую недоступность. Ручной ввод остаётся доступен.
- В дневнике показать сон на выбранную дату отдельно от заполненности анкеты. Импортированные значения отображаются с источником и временем получения. Ручной ввод и выбор между вариантами доступны на той же дате. Для прежних клиентов `wellness.sleep_minutes` остаётся совместимой проекцией ручного или исторического значения. Старый `PUT` с переданной длительностью обновляет ручной вариант, без поля сохраняет его, с `null` очищает ручной вариант и позволяет применить имеющийся Garmin. Сохранение анкеты новым интерфейсом само по себе не меняет выбор сна.
- В `read_inputs` и `calculate_measurements` добавить общую выборку выбранной длительности для диапазона G2–G5, включая ночи без `WellnessEntry`. Сохранять `has_entry` и `missing_diary_dates` по факту реальной анкеты. Формулы ATL, CTL, TSB, сравнение работоспособности, окно и пороги восстановления остаются прежними. G3 получает выбранное фактическое значение и источник из той же проекции, которую используют дневник и графики. После записи новые значения участвуют в расчётах при следующем запросе. Для открытых страниц предусмотреть обновление кэша React Query после своих действий и повторный запрос при завершении фонового импорта.
- Тренер видит выбранную длительность, источник, локальные даты пропусков, наличие наблюдений, отклонение от индивидуальной нормы, связанные предупреждения G3 и время последней успешной синхронизации при разрешённом подключении. В командной сводке предлагается фильтр «Все / Есть данные сна / Нет данных сна» по наличию наблюдения за последние семь завершённых дней в локальном поясе спортсмена, с отображением числа известных дней. Источник и наличие подключения не участвуют в оценке восстановления.

## 7. Предлагаемый план миграций

1. Добавить следующую ревизию Alembic поверх фактического `head` целевой ветки. В проверенной рабочей копии есть `0007_head_coach` поверх `0006_training_intelligence`. Уточнить `head` перед реализацией, сохранить линейную историю и обновить проверки, в которых текущая ревизия задана литералом. Новые таблицы ссылаются на профиль спортсмена, подключение и ночь, с индексом для диапазонов дат и ограничениями уникальности. [Текущая миграция G2](../backend/alembic/versions/0006_training_intelligence.py) · [Ревизия главного тренера](../backend/alembic/versions/0007_head_coach.py) · [Тест цепочки миграций](../backend/tests/test_access.py)
2. Перенести все исторические `wellness_entries.sleep_minutes`, у которых есть значение (`IS NOT NULL`), в `sleep_days` с меткой `legacy`, датой и снимком пояса из анкеты. Значение `0` сохранить как историческое наблюдение. Старые поля оставить для совместимости. Изменения через новые и старые маршруты согласовывать в одной транзакции. Во время обновления анкеты, ручного сна и импорта проверить конкурирующий сценарий, чтобы запрос с устаревшим состоянием не стирал выбор.
3. Проверить upgrade, downgrade и повторный upgrade на временной БД с прежними анкетами, `null` и `0`. Downgrade удаляет таблицы G6 и сохраняет анкеты с их совместимой длительностью. В старой схеме нет отдельного сна без анкеты, исходных вариантов и метаданных G6. Перед откатом нужен проверенный снимок исходной БД, если условия хранения его разрешают. При восстановлении в G6 история читается из снимка, подключение остаётся выключенным. Действующие токены и ключи в переносимую копию не включаются.
4. Рабочую миграцию проводить только после отдельного согласования и проверки резервной копии. Автоматический импорт включать независимо от релиза ручного дневника. Пригодность локальной настройки Garmin проверять на отдельной БД и разрешённом тестовом профиле.

## 8. Проверки G6.2–G6.5 после согласования

| Набор | Сценарии и критерии |
| --- | --- |
| Контракт и импорт | Фиктивные ответы Garmin с полной ночью, необязательными и отсутствующими полями, пустыми ночами и некорректными метками. Импорт создаёт одну ночь, повтор идемпотентен, обновление Garmin сохраняет исходник ручной правки, неполный ответ не уничтожает ранее сохранённое. Проверить ID, fallback без ID, конфликт нескольких сводок, ограничение 31 дня. |
| Ручной ввод | Спортсмен без часов сохраняет сон и анкету. Проверить ввод только длительности, обеих границ, переход через полночь, ручную правку длительности, `null`, сохранение старым клиентом и выбор источника. Охватить смену пояса, двусмысленное и несуществующее местное время при переводе часов и повторный импорт ранее привязанной ночи. |
| Ошибки и перезапуск | Действующий токен, истёкший токен, повторный обмен, истёкший или отозванный ключ, отказ доступа, отсутствие возможности, `429`, `Retry-After`, `5xx`, тайм-аут. Проверить один активный запуск при одновременных запросах, предел попыток, восстановление после обрыва транзакции и перезапуска, остановку устаревшей задачи при отключении, догрузку пропущенных дат и сохранение записей после отключения. |
| Аналитика и права | Смешанный ряд из ручных, исторических, импортированных и пропущенных ночей. Проверить 28-дневную медиану, повторный расчёт после выбора, отклонение и факты G3, отдельный пропуск анкеты и сохранение результатов нагрузки и работоспособности на контрольном наборе. Проверить чужие ID, роль тренера, отказ при неверном CSRF и Origin, закрытие реальной настройки на HTTP, отсутствие утечки ключа и токена в API, логах, диагностике и копии. |
| Совместимость, мобильный экран и PWA | Существующие анкеты до и после миграции, обратный переход, бэкап и восстановление, запуск без Garmin. Vitest и Playwright на production-сборке с временной БД проверяют профиль, дневник, оба источника, тренерский фильтр, состояния ошибок, экраны шириной 360–390 px и отсутствие API-ответов в кэше PWA. На G6.5 дополнительно проверить согласованный сценарий на физическом телефоне. |

Для CI использовать синтетические ответы и управляемое время. Реальные запросы к Garmin допускаются только в отдельно согласованной проверке после сверки условий. Начать с одного запроса за ночь с известными собственными данными владельца. Проверить статус, форму полей, единицы времени и поведение для пустой даты без вывода секретов и персональных значений в отчёт. Дальнейшую проверку истории и частоты проводить в пределах подтверждённого доступа.
