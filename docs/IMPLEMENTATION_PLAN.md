## Решения этапа A

- Backend владеет сессиями и ролями. Браузер и API работают на одном origin через Vite-прокси в разработке и через FastAPI при запуске сборки.
- SQLite использует WAL, внешние ключи и миграции Alembic. Схема расширяется по мере появления сущностей. База и прикладные данные отделены от статической сборки.
- Базовые маршруты включают вход, активацию, сброс пароля, разделы спортсмена, команду и управление доступом. Формы дневника, импорт, графики и интеграция появляются на соответствующих этапах.
- Тренер передаёт ссылки доступа получателю. Одноразовый секрет находится во фрагменте ссылки и отправляется API в теле запроса.

## Решения этапа B

- Тренеры редактируют профиль, историю массы, FTP и зоны. Спортсмен читает свой профиль и редактирует собственные дневники и RPE. Тренеры читают дневники и RPE всей команды. Заметки профиля доступны тренерам. Доступ проверяется в API для каждой операции.
- Запись дневника уникальна по спортсмену и календарной дате. Дата рассчитывается по зоне IANA из профиля, исходный пояс сохраняется в анкете. Время создания и изменения хранится в UTC. Новая анкета за будущую местную дату отклоняется. После смены пояса сохранённая анкета доступна для исправления по исходной дате.
- FTP действует с заданной местной даты до следующей записи. Будущее значение можно запланировать. Текущее значение выбирается на местную дату спортсмена. Исправление по той же дате меняет соответствующую запись и фиксируется в аудите. На этапе C расчёт тренировки сохраняет использованный FTP и параметры зон.
- История массы поддерживает несколько измерений за день с отдельными идентификаторами. Текущая масса берётся из последнего измерения по дате и порядку создания. Зоны мощности заданы в ваттах, зоны пульса — в ударах в минуту. Интервалы включают нижнюю границу и исключают верхнюю. Последнюю зону можно оставить открытой сверху.
- Импорт этапа C записывает момент старта в UTC (`workouts.started_at`) и активное время таймера в секундах (`workouts.timer_seconds`, FIT `session.total_timer_time`, включая движение и остановки при работающем таймере, исключая паузы таймера). Нагрузка session-RPE равна времени таймера в минутах × RPE. При отсутствии времени таймера нагрузка отсутствует, а оценка сохраняется. RPE связан с ID тренировки, поэтому несколько тренировок за один день оцениваются отдельно.
- Маршруты профилей, дневника и списка тренировок доступны под `/api/v1/athletes`, командная сводка под `/api/v1/wellness/team`, оценка тренировки под `/api/v1/workouts/{workout_id}/rpe`. Точные схемы и методы доступны в `/api/v1/docs`.

## Решения этапа C

- FIT декодируется общим `WorkoutImportService`. Оригиналы и история источников сохраняются отдельно от сводок и сжатых временных рядов.
- Точные совпадения файла и стабильный ID источника обеспечивают идемпотентность. Похожие записи FIT с разными хешами обозначаются для проверки.
- FTP на дату начала, границы зон, часовой пояс, версия формулы и параметры качества фиксируются рядом с результатом. Явное обновление параметров доступно тренеру при повторной обработке.
- Формулы, ограничения, настройки и список проверенных форматов описаны в [документации импорта FIT](FIT_IMPORT.md).

## Решения этапа D

- Код экспортёра MIT описывает закрытый мобильный протокол международного OnelapFit. Официальный публичный API для приложения не подтверждён. Прямой доступ выключен по умолчанию, а ручной FIT-импорт остаётся доступен.
- OnelapFitProvider использует явно настроенный HTTPS-шлюз. Пароли не сохраняются, токены шифруются и привязываются к владельцу, поколению подключения и origin. Отключение и деактивация удаляют локальную сессию.
- Межпроцессная блокировка выделяет один планировщик на файл БД. Очередь, журнал, отложенные повторы и отметка инкрементальной загрузки сохраняются в SQLite. Общий WorkoutImportService проверяет допустимость подключения перед фиксацией импорта.
- [Контракт шлюза, управление ключами и проверка реального аккаунта](ONELAPFIT_VALIDATION.md).

## Решения этапа E

- Командная таблица и индивидуальная аналитика строятся сервером по анкетам, импортированным FIT, сохранённым метрикам, RPE и истории FTP. В недельной нагрузке и зонах указывается покрытие, отсутствующие измерения сохраняются как пропуски.
- Периоды и предупреждения учитывают местную дату спортсмена. Общие пороги записываются в SQLite, изменения фиксируются в аудите. Предупреждения рассчитываются из текущих данных и доступны тренерам.
- У спортсмена числовая сводка тренировки, у тренера — тренды и графики сохранённых датчиков. История, проверка и ручной запуск OnelapFit доступны из обзора спортсмена.
- [Методика аналитики и настройки тренера](COACH_ANALYTICS.md).

## Решения этапа F

- Собранный frontend публикует manifest, иконки и worker. Кеш содержит только версионированные статические ресурсы. При переходе между версиями текущая вкладка обновляется после подтверждения, остальные не теряют введённый текст.
- Windows-сценарий запускает Uvicorn на loopback с отдельной миграцией и кооперативной остановкой. Сетевой вход предоставляется через проверенный HTTPS-прокси.
- SQLite Backup API копирует согласованный снимок WAL. Архив содержит проверенные оригиналы FIT и разрешённые параметры. Из снимка удаляются действующие сессии и отзываются открытые ссылки. Восстановление проверяет архив и создаёт отдельный каталог.
- Тестовая команда создаётся отдельно от рабочих данных. Фикстуры шлюза и автоматические браузерные тесты дополняют испытания на базе. Результаты и открытые пункты приведены в [отчёте](RELEASE_READINESS.md).
