# Техническое задание для Codex
# Cycling Team Monitor — версия 1.0

## 1. Цель проекта

Разработать полноценную систему мониторинга тренировок и состояния спортсменов национальной команды по велоспорту.

Система рассчитана на:
- 20 спортсменов;
- 3 тренеров с одинаковыми правами;
- возможное расширение количества пользователей.

Основная задача — автоматически получать тренировки из индивидуальных аккаунтов OnelapFit, обрабатывать FIT-файлы, собирать субъективные показатели состояния спортсменов и предоставлять тренерам инструменты мониторинга и анализа.

Необходимо создать работающее приложение, а не демонстрационный интерфейс.

**Основной язык интерфейса — русский.**

## 2. Платформы и архитектура

### 2.1. Первая версия

Приложение реализуется по принципу PWA-first.

Поддерживаемые устройства:
- Android — PWA через Chrome;
- Windows — PWA через Edge или Chrome;
- iPhone — адаптивная веб-версия/PWA через Safari.

Приложение должно иметь два интерфейса:
- спортсмена;
- тренера.

Роль определяется сервером после авторизации.

### 2.2. Перспектива развития

Архитектура должна допускать:
- Android APK через Capacitor;
- Windows EXE через Tauri;
- сохранение PWA для iPhone.

Не создавать APK и EXE в версии 1.0, но предусмотреть изоляцию платформозависимых функций.

### 2.3. Технологии

Frontend:
- React;
- TypeScript;
- Vite;
- React Router;
- TanStack Query;
- адаптивный интерфейс;
- PWA manifest и service worker;
- библиотека графиков Recharts.

Backend:
- Python;
- FastAPI;
- SQLAlchemy;
- Alembic;
- SQLite с включённым WAL;
- Pydantic;
- Python-библиотека для чтения FIT;
- планировщик фоновой синхронизации.

Тестирование:
- pytest для backend;
- Vitest для frontend;
- Playwright для основных пользовательских сценариев.

Не добавлять платные обязательные зависимости.

## 3. Принципы разработки

1. Все данные принадлежат конкретным спортсменам.
2. Права доступа проверяются на сервере.
3. Исходные FIT-файлы сохраняются.
4. Сырые данные тренировок сохраняются для повторного анализа.
5. Расчётные показатели можно пересчитывать.
6. Изменение FTP не должно незаметно изменять исторические расчёты.
7. Автоматическая синхронизация должна быть устойчивой к перезапускам.
8. Повторный импорт не должен создавать дубликаты.
9. Отсутствие соединения с OnelapFit не должно блокировать дневники и другие функции при работающем сервере.
10. Никакой обязательной офлайн-работы клиентов в версии 1.0.

## 4. Пользователи и авторизация

### 4.1. Роли

**Спортсмен:**
- видит только собственные данные;
- заполняет дневник;
- просматривает свои тренировки;
- вводит RPE;
- управляет собственным подключением OnelapFit.

**Тренер:**
- видит всех спортсменов;
- просматривает командную аналитику;
- управляет профилями спортсменов;
- просматривает историю тренировок;
- управляет приглашениями;
- видит статусы синхронизации;
- может запускать синхронизацию и повторную обработку.

Все три тренера имеют равные права.

### 4.2. Регистрация

Система закрытая.

Не допускается публичная регистрация.

Предусмотреть:
- создание первого тренера через безопасную команду инициализации;
- приглашения с одноразовым токеном и сроком действия;
- установку пароля;
- безопасный сброс пароля через административную процедуру;
- деактивацию аккаунтов;
- журнал важных действий.

Пароли приложения хранить только в виде устойчивых хешей, например Argon2id.

Использовать безопасные HttpOnly cookies для сессий, CSRF-защиту при cookie-based аутентификации, ограничения попыток входа и серверную проверку прав.

- масса тела;
- специализация;
- команда/группа;

- текущий FTP;
- история FTP;
- индивидуальные зоны мощности;
- индивидуальные зоны пульса, если настроены;

Предусмотреть хранение истории измерений массы тела.

Лабораторные исследования и лактатные тесты не реализовывать полноценно в версии 1.0, но не блокировать их последующее добавление.

## 6. Утренний дневник

Спортсмен ежедневно заполняет одну анкету.

Поля:
- дата;
- качество сна — 1–5;
- общая усталость — 1–5;
- усталость ног — 1–5;
- мотивация — 1–5;
- настроение — 1–5;
- мышечная болезненность — 1–5;
- симптомы заболевания — да/нет;
- комментарий — необязательный;
- время создания и изменения.

Направление шкал должно быть явно подписано в интерфейсе.

Для качества сна, мотивации и настроения: 1 — очень плохо, 5 — отлично.

Для общей усталости, усталости ног и мышечной болезненности: 1 — минимальная, 5 — очень высокая.

Одна анкета на календарную дату спортсмена. Должна поддерживаться корректировка анкеты с фиксацией времени изменения.

Тренер видит:
- кто заполнил дневник;
- кто не заполнил;
- значения за сегодня;
- историю;
- графики;
- изменения относительно индивидуального уровня;
- предупреждения.

Время и календарная дата определяются в настроенной временной зоне спортсмена.

## 7. RPE

После каждой тренировки спортсмен вводит субъективную оценку сложности.

Шкала: 0–10.

RPE привязывается к конкретной тренировке.

Один спортсмен может выполнить несколько тренировок за день.

Предусмотреть:
- напоминание в интерфейсе об отсутствии RPE;
- редактирование;
- время заполнения;
- необязательный комментарий.

Рассчитывать session-RPE load как длительность тренировки в минутах × RPE. Использовать единую документированную методику длительности.

## 8. Автоматическая интеграция OnelapFit

### 8.1. Основная цель

Каждый спортсмен подключает собственный аккаунт OnelapFit, используя электронную почту или телефон и пароль.

После подключения сервер автоматически получает новые тренировки.

Спортсмен не должен вручную скачивать FIT-файлы при нормальной работе интеграции.

### 8.2. Важное ограничение

Официальный публичный API OnelapFit не подтверждён.

В качестве исследовательской основы рассмотреть:

https://github.com/just-nobody/onelap-fit-export

Не предполагать, что сторонний проект гарантированно совместим с текущим OnelapFit.

До реализации изучить исходный код, лицензию, требования, механизм авторизации, поддерживаемые домены, структуру ответов и возможность получения оригинальных FIT-файлов.

Не копировать код без проверки условий лицензии.

Не обходить CAPTCHA, 2FA или другие механизмы защиты.

Если авторизация требует интерактивного подтверждения, показывать соответствующий статус и инструкции.

### 8.3. Архитектура интеграции

Создать независимый адаптер:

`OnelapFitProvider`

Предусмотреть интерфейс операций:
- подключение аккаунта;
- проверка подключения;
- получение списка тренировок;
- получение метаданных тренировки;
- скачивание FIT;
- обновление/проверка авторизации;
- отключение аккаунта;
- обработка ошибок.

Не смешивать реализацию протокола OnelapFit с обработкой FIT.

Создать отдельный сервис:

`WorkoutImportService`

Все источники тренировок должны использовать один общий механизм обработки.

### 8.4. Подключение аккаунта

В профиле спортсмена раздел «OnelapFit».

Функции:
- ввод логина и пароля;
- подключение;
- проверка;
- отключение;
- повторное подключение;
- просмотр статуса;
- время последней успешной синхронизации.

Учётные данные OnelapFit хранить зашифрованно на сервере с использованием ключа из переменных окружения.

Не сохранять пароли в логах.

Не показывать пароли тренерам.

Не отправлять пароли в аналитические системы.

Учитывать, что шифрование секретов не устраняет риски хранения сторонних паролей. Предусмотреть удаление секретов при отключении аккаунта.

### 8.5. Автоматическая синхронизация

Настраиваемый интервал, по умолчанию 15 минут.

Система должна:
1. Получить список подключённых аккаунтов.
2. Проверить необходимость синхронизации.
3. Обратиться к OnelapFit.
4. Получить список тренировок.
5. Найти новые или изменённые записи.
6. Скачать FIT-файлы.
7. Передать их общему сервису импорта.
8. Сохранить результаты.
9. Обновить статус подключения.

Предусмотреть:
- последовательную или ограниченно параллельную обработку;
- ограничение частоты запросов;
- повторные попытки с увеличивающейся задержкой;
- обработку 429 и временных ошибок;
- защиту от одновременной синхронизации одного аккаунта;
- продолжение работы после перезапуска;
- журнал результатов;
- ручной запуск синхронизации;
- первоначальную загрузку истории тренировок;
- возможность ограничить глубину загрузки истории.

Если сервер выключен, синхронизация не выполняется. После включения система должна возобновить проверки и получить пропущенные тренировки, если они доступны у провайдера.

Не заявлять гарантированную синхронизацию, пока интеграция не проверена на реальном аккаунте.

### 8.6. Статусы подключения

- Не подключено.
- Проверка подключения.
- Подключено.
- Синхронизация выполняется.
- Синхронизировано.
- Требуется повторная авторизация.
- Временная ошибка.
- Интеграция недоступна.
- Ожидает проверки на реальном аккаунте.

Статусы должны отображаться понятным русским текстом.

### 8.7. Защита от дублей

Использовать:
- внешний ID тренировки, если доступен;
- ID спортсмена и источник;
- хеш содержимого FIT-файла;
- дополнительные признаки тренировки для обнаружения потенциальных дублей.

Уникальность должна обеспечиваться ограничениями БД и идемпотентной обработкой.

Одинаковый FIT, полученный через OnelapFit и ручную загрузку, не должен создавать две тренировки одному спортсмену.

При обнаружении совпадения из разных источников сохранять информацию о происхождении, не дублируя тренировку.

### 8.8. Резервный импорт

Реализовать ручную загрузку FIT через PWA.

Это обязательная функция, даже если автоматическая синхронизация работает.

Пользователь должен видеть результат импорта и причину ошибки.

## 9. Обработка FIT

### 9.1. Данные тренировки

Извлекать, если присутствуют:
- дата и время начала;
- длительность;
- время движения;
- дистанция;
- средняя и максимальная скорость;
- набор высоты;
- средняя и максимальная мощность;
- средний и максимальный пульс;
- средний и максимальный каденс;
- температура;
- GPS-данные;
- доступные дополнительные поля.

Отсутствующие значения показывать как «Нет данных», не подставлять нули.

### 9.2. Временные ряды

Сохранять:
- временные отметки;
- мощность;
- пульс;
- каденс;
- скорость;
- высоту;
- координаты, если есть.

Не предполагать, что каждое устройство записывает одинаковый набор полей или строго одну запись в секунду.

### 9.3. Расчётные показатели

Реализовать:
- NP;
- IF;
- TSS;
- время в зонах мощности;
- время в зонах пульса;
- распределение мощности;
- session-RPE load.

Расчёты должны учитывать пропуски данных, паузы и качество временного ряда.

Если данных недостаточно, показатель не рассчитывается, а причина фиксируется.

Для IF и TSS использовать FTP, действовавший на дату тренировки, либо явно сохранённый FTP, использованный при расчёте.

Хранить версию алгоритма расчёта и использованные параметры, чтобы результаты можно было воспроизвести.

### 9.4. Проверка качества

Предусмотреть:
- валидацию структуры FIT;
- ограничение размера файла;
- проверку расширения и фактического содержимого;
- обработку повреждённых файлов;
- фиксацию отсутствующих каналов данных;
- защиту от некорректных значений;
- возможность повторной обработки.

Исходные файлы хранить вне публичного каталога веб-сервера.

- резервное копирование;
- восстановление после перезапуска;

Планировщик синхронизации должен работать в единственном экземпляре, без дублирования задач при нескольких процессах backend.

Не требовать постоянного включения ноутбука для сохранности уже записанных данных. Однако при выключенном сервере приложение и синхронизация недоступны.
