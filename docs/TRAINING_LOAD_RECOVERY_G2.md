# Cycling Team Monitor 2.0 — аналитическое ядро G2

G2 добавляет серверные расчёты нагрузки, восстановления, контрольных усилий и временных связей. API возвращает измерения и основания для сравнения. Командная сводка, предупреждения A–F и пользовательские экраны относятся к G3–G4. [Согласованный план G1](TRAINING_LOAD_RECOVERY_PLAN.md)

## Схема и источники

- Миграция `0006_training_intelligence` добавляет к `wellness_entries` nullable-поля `sleep_minutes` (0–1440), `recovery` (1–5) и `training_day_status` (`rest` / `all_workouts_recorded`). Исходные записи сохраняются. Пропуск поля в запросе старого клиента сохраняет предыдущее значение. Явный `null` очищает его. Спортсмен отмечает завершившийся день через существующий маршрут дневника.
- Таблица `workout_efforts` хранит одну тренерскую разметку на существующую тренировку, код протокола, начало и длительность отрезка, его среднюю мощность, хеш файла и версию расчёта. Проекция мощности отрезка хранится рядом с разметкой, поэтому обычный пересчёт того же FIT сохраняет её. После замены файла или версии алгоритма разметка видна, но её измерение исключается до повторной проверки тренером.
- Лучшие мощности рассчитываются при FIT-импорте и сохраняются в служебной части `workout_metrics.result`. Для старого FIT их можно запросить отдельно по одной тренировке. Сервер рассчитает их из сохранённых блоков и таймера, без массового пересчёта. Сводка показывает поле `best_power` как `null`, пока для старой тренировки нет сохранённой проекции. Для разметки старого FIT также используются сохранённые блоки.
- Пороги модуля сохраняются отдельно в `app_settings`. Настройка существующих предупреждений, исторические FTP/TSS, правила импорта и пути развёртывания сохранены. `TSS`, `NP` и `IF` берутся из результата импорта. `session-RPE = RPE × минуты таймера`.

## Нагрузка и покрытие

Дни строятся по двум локальным полуночам в IANA-поясе профиля. Начало тренировки хранится в UTC. Дата анкеты берётся из дневника. Смена пояса перегруппирует тренировки, сохранив исходный снимок FTP. Текущий день предварительный. Недельные сравнения, повторные изменения результатов и статистика используют завершённые даты.

| Статус дня | Как день входит в расчёт |
| --- | --- |
| `rest` | Подтверждённый отдых без тренировок. TSS равен нулю. |
| `all_workouts_recorded` | Спортсмен подтвердил полноту записей. Для расчёта TSS нужен у каждой тренировки. |
| `imported` | Есть записи, полнота неизвестна. При известных TSS всех записей день участвует с ограниченным покрытием. |
| `unknown` | Нет тренировок и подтверждения. В ряду разрыв. |
| `conflict` | Отдых с тренировкой, полнота без тренировок или спорные дубликаты. День исключается из сглаживания и сравнений, исходные строки доступны для проверки. |

Покрытие содержит число календарных и известных дней, число дней с непротиворечивым подтверждением, число тренировок и число тренировок с TSS. `recorded_tss` сохраняет сумму измеренных TSS для просмотра исходных записей. На спорном дне эта сумма может включать обе записи, а `tss` для расчётов остаётся пустым. Точные дубликаты FIT дают один `workout_id`. Пары, похожие по правилам импорта, показываются как кандидаты.

Для ATL и CTL период `N` по умолчанию равен 7 и 42 календарным дням. Пусть `q = exp(−1/N)`, `α = 1 − q`. На первом известном дне `S = TSS`, `W = 1`. На следующем известном дне `S = qS + α × TSS`, `W = qW + α`, значение равно `S/W`. На неизвестном дне `S` и `W` только умножаются на `q`, а точка на графике остаётся пустой. TSB на конец дня равен `CTL − ATL` за тот же день. По каждому периоду возвращается отдельное покрытие. Статус `sufficient` требует полностью подтверждённых и известных дней в окне длиной `N`. До этого оценки помечены как `partial` или `insufficient`. TSB наследует более слабый из статусов. Выборка ограничена окном анализа и запасом прогрева до трёх периодов CTL перед его началом.

Дневная норма — медиана доступных TSS за предыдущие 28 дней, от 14 известных дат по умолчанию. Серия повышенных дней растёт при превышении положительной нормы на 20% и прерывается при пропуске. Семидневная норма — медиана минимум трёх из четырёх предыдущих непересекающихся недель с таким же количеством известных дней, минимум пять из семи в каждой. Разница в процентах равна `100 × (значение − норма) / норма`. При нулевой норме возвращается только абсолютная разница. Недели с конфликтами исключаются из сравнения. Для неполных недель процент относится к наблюдаемой нагрузке. В ответе есть суммы и покрытие самих недель сравнения.

## Восстановление и контрольные усилия

- База каждого показателя — медиана наблюдений в диапазоне от `d−28` до `d−1`, минимум семь измерений по умолчанию. Длина окна и минимум настраиваются. Пропуски сохраняются. Ухудшение по умолчанию равно одному баллу по соответствующей шкале или 45 минутам сна относительно собственной медианы. Для устойчивого ухудшения нужны минимум четыре оценённых дня за неделю и минимум два дня с несколькими ухудшившимися показателями из разных групп. Например, длительность и качество сна входят в одну группу.
- Размеченный отрезок задаётся полуоткрытым диапазоном от начала FIT. Каждая секунда должна быть покрыта мощностью в одном активном сегменте по действующим правилам таймера и короткого удержания сигнала. Нулевые измерения допустимы. Пауза, пропуск или неполный интервал исключают отрезок. За произвольные поездки возвращаются описательные лучшие 5 с, 1, 5 и 20 минут.
- Сопоставимость задаёт тренер кодом протокола. Для одного спортсмена сравниваются только измерения с точно совпадающими кодом и длительностью. Последняя измеренная попытка каждой предыдущей даты используется для медианы, минимум три даты за 90 дней. Повторное изменение требует две последние размеченные попытки на разных завершённых датах, обе с отклонением в одну сторону хотя бы на `performance_change_pct` (по умолчанию 5%). Обе оцениваются относительно общей базы до первой из них. Неизмеренная или устаревшая последняя попытка блокирует повторное изменение. Сравнение RPE доступно для полноформатных попыток с сопоставимой мощностью. Запись FTP показана как история профиля.

## Временные связи

- Эпизод начинается с превышения дневной нормы или перехода недельной нагрузки через порог. Пересекающиеся семидневные окна объединяются. Уникальная реакция по дате, показателю и ID тренировки относится к ближайшей предшествующей дате повышенной нагрузки в эпизоде. Отдельно видны задержки 0, 1, 2, 3 и 4–7 дней, граница наблюдения и признак открытого окна. При совпадении дат порядок событий неизвестен. Возврат к норме требует две измеренные даты после ухудшения и последней даты нагрузки в окне эпизода.
- Корреляция Спирмена рассчитывается отдельно по спортсмену, показателю и задержке 0…7 дней в пределах 180 завершённых суток. Одна пара на дату нагрузки и задержку. Если в день несколько попыток одного протокола, статистика использует медиану их отклонений. Для коэффициента нужны минимум 30 известных пар и вариативность обоих рядов. Проверка устойчивости требует минимум 12 пар в каждой хронологической половине, совпадающий знак и минимальную абсолютную величину 0,1 в обеих половинах и полной выборке. Ответ содержит коэффициент, размер и период выборки, число пар с подтверждённой нагрузкой и коэффициенты половин. При малой выборке остаются датированные наблюдения. Корреляции описывают наблюдаемые связи. Соседние даты и оценки на соседних задержках могут зависеть друг от друга.

## API G2

Все пути ниже имеют префикс `/api/v1`. Маршруты модуля доступны тренеру. Изменения проходят существующие проверки Origin и CSRF и фиксируются в аудите.

| Метод и путь | Назначение |
| --- | --- |
| `GET /training-intelligence/athletes/{athlete_id}/measurements?period=28` | Дневной и недельный ряды с покрытием, дневник с отклонениями, FTP и контрольные сравнения, эпизоды и статистика. Периоды 7, 28, 42, 90 дней. |
| `GET /training-intelligence/settings` | Действующие параметры расчёта. |
| `PUT /training-intelligence/settings` | Полная замена параметров. Пропущенные параметры получают значения по умолчанию. Например, `{"performance_change_pct": 8}` выставляет порог 8% и сбрасывает остальные параметры к значениям по умолчанию. |
| `GET /training-intelligence/workouts/{workout_id}/best-power` | Описательные максимумы мощности с ключами длительности в секундах. |
| `GET /training-intelligence/workouts/{workout_id}/effort` | Разметка и её измерение либо `null`. |
| `PUT /training-intelligence/workouts/{workout_id}/effort` | Разметить отрезок. Пример тела: `{"protocol":"erg-5min","start_seconds":120,"duration_seconds":300}`. |
| `DELETE /training-intelligence/workouts/{workout_id}/effort` | Удалить разметку. |
| `PUT /athletes/{athlete_id}/wellness/{date}` | Существующий маршрут спортсмена. Принимает необязательные новые поля вместе с обычной анкетой. |

## Воспроизведение на синтетических данных

Из корня проекта в PowerShell выполните проверку. Она создаёт временную БД, прогоняет миграции и проверяет API с синтетическими FIT.

```powershell
.\.venv\Scripts\python.exe -m pytest backend/tests/test_training_intelligence.py backend/tests/test_training_intelligence_api.py -q
```

В тесте `test_control_efforts_and_config_use_access_checks_and_invalidate_on_fit_update` три предыдущих результата 190, 200 и 210 Вт дают норму 200 Вт. Два новых результата по 180 Вт дают −10% каждый. После замены FIT последнего результата повторное снижение исключается до проверки отрезка. Тест `test_measurements_link_observed_deterioration_without_mixing_athletes` демонстрирует разные недельные отклонения при одинаковой текущей нагрузке и проверяет связи на одном спортсмене.

Для ручной проверки используйте документацию API `/api/v1/docs` на локальном стенде с тестовой базой. После входа под тестовым тренером запросите `measurements?period=7` и сверяйте `current_week.coverage`, даты эпизодов и `performance.repeated_changes`. Для записи используйте сессионную cookie, разрешённый Origin и заголовок `X-CSRF-Token`.

## Ограничения G2

- Стресс, пульс покоя, HRV, внешний журнал тестов и выполнение плана пока не поддерживаются. Сопоставимость в рамках протокола зависит от качества тренерской разметки и условий измерения.
- Одновременные изменения служат описанием наблюдений. Показатели подвержены влиянию пропусков, смены пояса, отсутствия подтверждения полноты и контекста, который не записан в FIT или дневнике.
- Разметка, новые поля дневника и аналитика доступны через API. Их экраны, предупреждения и производительность командного запроса проверяются после G2.
