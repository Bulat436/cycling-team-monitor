# Cycling Team Monitor 2.0 — объяснимые предупреждения G3

Предупреждения рассчитываются при запросе из измерений G2. Настройки хранятся в существующей записи `app_settings.training_intelligence`. G3 использует действующую схему БД. Предупреждения, подтверждения просмотра и история уведомлений отдельно не сохраняются. [План G1](TRAINING_LOAD_RECOVERY_PLAN.md) · [Формулы и покрытие G2](TRAINING_LOAD_RECOVERY_G2.md)

## Правила

| Код | Предупреждение | Условия по умолчанию | Уровень внимания |
| --- | --- | --- | --- |
| A | Возможное накопление усталости | TSS за семь завершённых суток на ≥20% выше индивидуальной нормы. В неделю оценены ≥4 дней, на ≥2 датах одного объединённого эпизода ухудшились показатели из ≥2 групп. Даты нагрузки и реакций для правила лежат в оцениваемой неделе. | Умеренный. Высокий при полном подтверждённом покрытии оцениваемой недели и недель сравнения и ≥3 датах ухудшения. |
| B | Рост нагрузки на фоне ухудшения восстановления | TSS вырос ≥15% относительно предыдущей сопоставимой недели. В текущей неделе устойчивое ухудшение, дней с ухудшением больше, чем в предыдущей оценённой неделе. Хотя бы один такой день входит в последние три завершённых дня. | Умеренный. Оценка покрытия относится к двум неделям, используемым в этом сравнении. |
| C | Возможное снижение работоспособности | G2 подтвердил отклонение мощности вниз ≥5% в двух новых попытках на разных днях. Общая база включает ≥3 предыдущих дат с валидными попытками того же спортсмена, протокола и длительности. Последняя попытка входит в последние 14 завершённых дней. | Умеренный. |
| D | Признаки положительной адаптации | Недельный TSS на ≥20% выше нормы при полном подтверждённом покрытии оцениваемой недели и недель сравнения. Обе новые попытки в текущей неделе улучшились ≥5% по правилам G2. За неделю оценены ≥4 дней восстановления без признака устойчивого ухудшения. | Информационный. |
| E | Недостаточность данных | Мало сопоставимых недель для индивидуальной нормы, меньше семи анкет за 14 завершённых дней или меньше четырёх оценённых дней восстановления в текущей неделе. Вывод перечисляет конкретные пробелы. | Информационный. |
| F | Восстановление после нагрузочного блока | G2 нашёл в едином эпизоде возвращение ранее ухудшившихся показателей к их индивидуальной норме минимум в двух наблюдаемых днях. Последняя подтверждающая дата входит в последние 14 завершённых дней. | Информационный. Открытое окно наблюдений или неполное покрытие нагрузки помечаются как частичное покрытие. |

Дневник со сном и усталостью в одну дату может содержать два независимых признака. Качество и длительность сна образуют одну группу. Для F абсолютное отклонение каждого ранее ухудшившегося показателя должно стать меньше его порога. Если G2 обнаружил возврат к норме после ухудшения, соответствующие даты не поддерживают активные A и B. При одновременных A и B в одном эпизоде ответы используют общий `episode_id` и взаимные `related_warning_ids`. Пропуски и спорные дни учитываются по правилам покрытия G2. Отсутствие сопоставимого протокола видно по `performance_status` и блокирует C и D.

## Настройки правил

Тренер читает и сохраняет настройки через существующий `GET/PUT /api/v1/training-intelligence/settings`. `PUT` полностью заменяет объект настроек. Для изменения одного параметра прочитайте текущий объект, измените поле и отправьте весь объект с Origin и CSRF.

| Поля | Что настраивают |
| --- | --- |
| `high_load_pct`, `warning_high_worsened_days`, `warning_growth_pct`, `warning_growth_recent_days` | Отклонение недельного TSS от нормы, переход A к высокому приоритету, рост к предыдущей неделе и давность ухудшения для B. |
| `weekly_min_days`, `weekly_min_baseline_blocks`, `load_baseline_min_days` | Необходимую историю нагрузки. Для недельной нормы сохраняется минимум три сопоставимых блока. |
| `recovery_window_days`, `recovery_min_observations`, `recovery_score_delta`, `recovery_sleep_delta_minutes` | Индивидуальную шкалу сравнения, достаточность истории и минимальное отклонение по показателю. |
| `recovery_min_groups`, `recovery_min_evaluated_days`, `recovery_min_worsened_days`, `recovery_normalization_days` | Покрытие групп, устойчивость ухудшения и число наблюдаемых дней возврата к норме. |
| `performance_change_pct`, `performance_baseline_attempts`, `performance_repeat_attempts`, `performance_window_days` | Отклонение мощности и сопоставимую историю. Схема сохраняет нижние пределы три предыдущие и две новые попытки. |
| `warning_recent_days`, `warning_diary_window_days`, `warning_diary_min_entries` | Давность C и F, длину окна дневника и минимум заполненных дат для E. |

Высокий приоритет отсчитывается от числа дат ухудшения и требует полного покрытия нагрузки. Он задаёт порядок просмотра. Недельные сравнения используют семь завершённых суток в поясе спортсмена. Окно реакции после нагрузки — до семи суток по G2.

## API

Все пути имеют префикс `/api/v1/training-intelligence`. Ответы приватных маршрутов передаются с `Cache-Control: no-store`.

| Маршрут | Доступ и ответ |
| --- | --- |
| `GET /athletes/{athlete_id}/warnings` | Тренер. Предупреждения спортсмена, недельная нагрузка и покрытие, сводка восстановления, статус работоспособности и дата последнего завершённого дня. |
| `GET /team` | Тренер. Та же сводка для каждого спортсмена. Строки упорядочены по максимальному уровню внимания, затем по имени и ID. |
| `GET /me` | Спортсмен. Собственная нагрузка и записи восстановления с индивидуальными базами и пропусками. ID берётся из авторизованной сессии. |
| `GET /athletes/{athlete_id}/measurements` | Существующий API G2 для проверки первичных расчётов и дат. В эпизодах добавлены факты повышения нагрузки и число наблюдений в реакциях. В контрольных сравнениях доступны исходные попытки базы. |

У предупреждения есть `id`, тип, название, уровень внимания, период, объяснение и ограничения. `facts` содержит фактическое значение, базу, отклонение и единицу, даты и объём выборки. Для реакции при наличии связи возвращаются дата нагрузки и задержка. `workouts` содержит датированные ссылки по ID, с ролью тренировки в доказательстве. `coverage` показывает применимые счётчики, даты и причины нехватки данных. `thresholds` перечисляет основные пороги срабатывания. Значения сравниваются до округления.

## Проверка на синтетических данных

Из корня проекта в PowerShell выполните:

```powershell
.\.venv\Scripts\python.exe -m pytest backend/tests/test_training_warnings.py -q
```

Тесты покрывают все шесть типов, равенство порогу, неполное и конфликтное покрытие, разные протоколы и длительности, устаревшую разметку, пропуски и отсутствие ложных срабатываний. Интеграционный тест проверяет маршруты для тренера, двух спортсменов и гостя, сортировку команды по приоритету, локальные сутки и применение настроек.

Для ручной проверки на локальном стенде с синтетической базой войдите тестовым тренером и откройте `/api/v1/training-intelligence/team` на том же адресе. Возьмите `athlete_id` из ответа и запросите `/api/v1/training-intelligence/athletes/{athlete_id}/warnings`. Сверьте предупреждение с `/measurements?period=28` для этого спортсмена: неделю сравнения, датированные факты дневника и ID контрольных попыток. Для спортсмена проверьте свою сводку по `/api/v1/training-intelligence/me`. Базовую тестовую команду создаёт `backend/tests/seed_team.py` в отдельном каталоге. Её редкий дневник демонстрирует E. Полный набор A–F воспроизводится автоматическими сценариями выше.

## Ограничения

- Предупреждения описывают наблюдения в пределах выбранных правил и первичных записей. Связь по датам не устанавливает причину изменения. При совпадении дат порядок внутри дня неизвестен.
- Для C и D вывод относится к размеченному протоколу. Условия тестирования сопоставляет тренер. Отдельные независимые протоколы одного спортсмена могут показывать разные направления.
- Командный запрос читает тренировки, анкеты и готовые проекции пакетно. Экраны и замер производительности на синтетической команде относятся к последующим этапам.
