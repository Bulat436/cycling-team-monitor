# CTM 2.0 — результаты проверки G5

**Статус — READY WITH LIMITATIONS.** Синтетическая проверка поддерживает ограниченный пилот одной команды. Установка PWA на физических телефонах, удалённый вход на целевом адресе и проверка оригинальных FIT используемых устройств остаются отдельными шагами. [Оценка готовности и условия допуска](RELEASE_READINESS.md)

## Что проверено

- Синтетический набор из 20 спортсменов и трёх тренеров воспроизводит историю до 49 дней в четырёх часовых поясах. Для каждого спортсмена задан полный ожидаемый набор предупреждений, включая отсутствие сигналов. Все 20 результатов совпали. Отдельно сверены числа доказательств, приоритеты, покрытие и единый эпизод для связанных A и B. [Матрица и независимые эталоны](ANALYTICS_VALIDATION.md)
- Пройдены контрольные случаи ATL/CTL/TSB, исходного веса сглаживания, 28-дневной медианы, недостаточной выборки, корреляции Спирмена, задержек до семи суток, объединения эпизодов и исторического FTP. Сопоставление старых и новых контрольных отрезков использует измеренную мощность и общий протокол.
- Три тренера получили одну сводку авторизованной команды. Спортсмен видит собственную сводку, запросы чужих данных и тренерских маршрутов отклоняются. Проверены неверные параметры, повреждённый CRC, повторная загрузка под новым именем и общие коды ошибок без упоминания исходных данных.
- На временных БД пройдены миграции от пустой схемы до главы, обратный прогон и обновление заполненной базы `0005_coach` с проверкой строк тренировок, блоков и байтов FIT. Резервная копия и восстановление сохранили значения предупреждений, контрольные отрезки и оригиналы FIT. Восстановленный стенд запросил новый вход. Штатный Windows-рантайм дважды запущен отдельными процессами и штатно остановлен на изолированных путях. После обычного перезапуска сессия и командная сводка сохранились.
- Браузерные сценарии проходят от командной панели через предупреждение, графики и связанный FIT до истории контрольных попыток, а также от личной сводки до сохранения дневника и появления данных в графике. Проверены три профиля Chromium, включая ширину 320 пикселей для экрана тренера.

В тесте перезапуска Windows используются временная БД и минимальный комплект файлов для старта приложения. Полная production-сборка с manifest, иконками и service worker проверяется отдельно браузерными сценариями.

## Обнаруженный дефект

При полном отключении сети библиотека запросов откладывала чтение API, а экран мог оставаться в состоянии загрузки. Для запросов и сохранений теперь проверяется доступность сервера того же origin независимо от индикатора сети браузера. При недоступности появляется ошибка, введённая анкета остаётся в форме, после восстановления связи данные обновляются. Сохранение можно повторить вручную. Регрессионные сценарии проверяют отключение и восстановление связи, а также повторную отправку анкеты. Внешние запросы браузера блокировались отдельно, при этом локальный сервер оставался доступен.

В подготовительных прогонах исправлены ожидания самих тестов. Для обновления истории FTP раздельно проверяются изменившийся график и неизменные снимки FIT. Тестовая сессия переиспользуется с действующим лимитом входа. Браузерный сценарий проверяет полотно графика отдельно от значков легенды и ищет ссылку по факту в конкретной строке предупреждения.

## Производительность

Замеры выполнены на Windows с Python 3.13.17 и Node.js 24.12.0. После отдельного первого запроса выполнено 20 последовательных запросов на маршрут через FastAPI TestClient с разбором JSON. Время включает приложение и SQLite. Задержки браузера и удалённого доступа в него не входят.

| Маршрут | Первый запрос | p95 | Максимум | SELECT на запрос |
| --- | ---: | ---: | ---: | ---: |
| Команда, 20 спортсменов | 859,7 мс | 819,4 мс | 843,2 мс | 6 |
| Карточка, период 90 дней | 55,0 мс | 69,7 мс | 131,4 мс | 9 |

Порог p95 в одну секунду пройден в этом прогоне. На каждом маршруте выполнялись по одному запросу тренировок и дневника. Запросы к сырым блокам FIT отсутствовали. История набора содержит до 49 дней, даже когда карточка запрашивает период 90 дней. Одновременная работа нескольких тренеров и задержки за пределами loopback в этот замер не входят.

## Воспроизведение

Из корня отдельной копии репозитория в PowerShell выполните проверки. Сборку подготовьте в этой же изолированной копии. Для подачи временной сборки тестовому серверу можно указать `CTM_E2E_STATIC_ROOT`. Подкаталог `frontend/dist` должен содержать собранный интерфейс и PWA.

```powershell
.\.venv\Scripts\python.exe -m pytest backend/tests -q
.\.venv\Scripts\python.exe -m pytest backend/tests/test_training_pilot.py -q -s
npm.cmd --prefix frontend test -- --configLoader runner
npm.cmd --prefix frontend run build
npm.cmd --prefix frontend run test:e2e
$env:CTM_E2E_G5 = '1'
try { npm.cmd --prefix frontend run test:e2e }
finally { Remove-Item Env:CTM_E2E_G5 }
```

Playwright создаёт отдельную БД на запуск. Для ручной проверки той же команды можно запустить `backend/tests/run_e2e.py` с `CTM_E2E_G5=1`, адресом loopback в `CTM_E2E_ORIGIN`, новым временным каталогом в `CTM_E2E_DIRECTORY` и тестовым паролем в `CTM_E2E_PASSWORD`. Временная сборка выбирается той же переменной `CTM_E2E_STATIC_ROOT`. Первый тренер — `pilot-coach1@example.com`. [Чек-лист тренера](PILOT_TEST_CHECKLIST.md)

## Ограничения

Синтетические данные подтверждают соответствие правилам в заданных сценариях. Они не оценивают точность выводов на реальных спортсменах и чувствительность к фактическим пропускам импорта, условиям контрольных тестов и смещению дневниковых оценок. Пилот требует сверки спорных сигналов с исходными датами и данными. Числовая или временная связь не устанавливает причину.

Содержимое API требует связи с сервером. При полной потере связи PWA не предоставляет автономного доступа к личным данным и не отправляет формы позже автоматически. Нативная установка, запуск и обновление на физическом Android и iPhone требуют ручной проверки. [Инструкция для телефонов](PILOT_PHONE_CHECK.md)
