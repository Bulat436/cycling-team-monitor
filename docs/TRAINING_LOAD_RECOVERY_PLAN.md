### Изменения схемы, предлагаемые для MVP

- После `0005_coach` добавить к `wellness_entries` три необязательных поля: продолжительность сна в минутах, самооценку восстановления 1–5 и подтверждение полноты сведений за день (`rest` / `all_workouts_recorded` / `null`). Отметку спортсмен может поставить за завершившийся день. При появлении тренировки в подтверждённый день отдыха показываем конфликт. Прежние записи читаются с `null`, а сохранение из старого клиента с пропущенным полем сохраняет его текущее значение. Явный `null` очищает поле.
- Добавить `workout_efforts` для тренерской разметки одного контрольного усилия на тренировку. Ссылка на существующую тренировку, код протокола, начало от старта FIT в секундах и длительность позволяют использовать старые записи. Код протокола тренер повторно использует для одинаковой задачи, режима и условий измерения. Разметка содержит идентификатор использованной версии FIT. Если импорт изменил файл, тренер перепроверяет интервал. API записи использует защиту тренерской роли, Origin, CSRF и аудит.
- Использовать существующий `app_settings` с отдельным ключом и валидируемой схемой для порогов модуля. Сводки вычислять при запросе. Первоначальная миграция добавляет только nullable-поля и новую таблицу, существующие данные сохраняются. Стресс, пульс покоя, HRV и внешние результаты тестов остаются точками расширения. Выполнение плана имеет статус «Показатель не поддерживается».

## Методика расчётов

### Тренировочная нагрузка

- Для каждой тренировки возвращать дату, TSS, NP, IF, длительность, RPE, session-RPE и причины пропусков. Для каждого дня и недели возвращать сумму измеренного TSS и число тренировок с известным и неизвестным TSS. Интенсивная тренировка для сводки — `IF ≥ 0,85` и таймер от 20 минут по сохранённым метрикам. Дни отдельно отмечать как подтверждённый отдых, дни с импортом и дни без подтверждения. Для сглаживания и сравнений день известен, если он подтверждён как отдых либо содержит тренировки с рассчитанным TSS для каждой записи и без конфликта. Подтверждение отдыха и полноты импорта дополнительно влияют на статус покрытия. Ноль в дневном ряду означает измеренный ноль или явное подтверждение отдыха. Пропуск остаётся разрывом.
- Суточная дата тренировки определяется началом в текущем IANA-поясе профиля, как в действующей аналитике. Границы задаются двумя локальными полуночами. Для анкет используется сохранённая дата записи, для IF/TSS — сохранённый снимок параметров импорта. Смена пояса может перегруппировать тренировки по дате. Записи с началом позже времени расчёта исключаются. Текущие незавершённые сутки показываются на графике как предварительные, а недельное сравнение и активные правила опираются на завершившиеся сутки.
- ATL и CTL — экспоненциальное сглаживание дневного TSS с параметром `α = 1 − exp(−1/N)`. Периоды `N` по умолчанию 7 и 42 календарных дня. На первом наблюдении `S = TSS`, `W = 1`. Далее `S = (1−α) × S + α × TSS`, `W = (1−α) × W + α` на известном дне. В день с неизвестным TSS затухают только `S` и `W`. При новом известном значении результат равен `S / W`. На самом пропуске график показывает разрыв. Подтверждённые дни отдыха входят в расчёт с нулём. TSB на конец дня — `CTL − ATL` за тот же день. На короткой истории показываем период прогрева, число известных дней и долю подтверждённых дней. Загружаем историю прогрева до `3 × max(N)` суток перед первым нужным днём. [Рекуррентная формула EWMA](https://www.itl.nist.gov/div898/handbook/pmc/section3/pmc324.htm)
- Недельная норма — медиана до четырёх предшествующих непересекающихся семидневных блоков. Для численного сравнения нужны минимум три блока и не менее пяти известных дней из семи в каждом блоке и в оцениваемой неделе. Сравниваем блоки с одинаковым числом известных дней либо полные блоки. Для неполных блоков процент относится к наблюдаемой нагрузке и показывается с покрытием и статусом «Частично достаточно». Сравнение при нулевой норме показывает только абсолютную разницу. Формула процента — `100 × (текущий TSS − обычный TSS) / обычный TSS`. Рост относительно непосредственно предшествующей недели вычисляется отдельно по тем же требованиям к покрытию.
- Дневная норма для серии повышенных дней — медиана дневных TSS за предыдущие 28 суток при наличии ≥14 известных дней с учётом подтверждённого отдыха. Порог превышения — +20% от положительной нормы, неизвестный день разрывает серию. Дневные пики при нулевой норме показываем отдельно без процента и без включения в серию.

### Восстановление

- По каждой метрике отдельно берём медиану наблюдений на датах `d−28…d−1`, по умолчанию от семи записей. Возвращаем число наблюдений, значение, медиану и разницу в исходных единицах. Оцениваем направленность по шкале: рост усталости и болезненности, снижение качества сна, длительности сна, восстановления, настроения и мотивации считаются ухудшениями. Общая усталость и усталость ног образуют одну группу для подсчёта независимых признаков. Порог отклонения для шкалы — 1 балл, для длительности сна — 45 минут относительно собственной медианы.
- Устойчивое ухудшение — минимум два разных показателя восстановления из разных групп в один день, повторившиеся минимум в два разных дня из последних семи с не менее чем четырьмя оценёнными днями. Например, качество и длительность сна считаются одной группой. Возврат к норме — минимум две оценённые записи после ухудшения в пределах семи суток после блока, где ранее ухудшившиеся показатели снова укладываются в порог и между этими записями нет измеренного повторного ухудшения. Дни без записей видны на шкале и не подтверждают улучшение.

### Работоспособность

- Показать историю FTP как историю измерений или настроек без вывода по одному изменению. Рассчитывать лучшие средние мощности за 5 с, 1, 5 и 20 минут при наличии непрерывного активного интервала. Каждая секунда окна должна быть покрыта интервалом показаний по правилам активного времени и короткого удержания сигнала, которые уже используются при расчёте мощности FIT. Нулевая измеренная мощность допустима. Пауза и разрыв ряда прекращают окно. Для размеченного отрезка действуют те же требования к покрытию. Лучшие мощности из произвольных тренировок остаются описательными.
- Для сравнения использовать контрольные усилия одного спортсмена, одного размеченного протокола и одинаковой длительности с валидным сигналом мощности. Сравнивать среднюю мощность размеченного отрезка с медианой ≥3 предшествующих сопоставимых попыток за 90 дней. Для предупреждения нужны ≥2 новые попытки в разные дни с отклонением в одном направлении минимум на 5%. Каждую оценивать относительно общей базы, предшествующей обеим попыткам. Сопоставлять RPE только для сопоставимых тренировок целиком, где известны выполненная мощность и длительность. Любительская поездка или неполный ряд дают статус «Недостаточно сопоставимых данных».
- Для старых FIT использовать уже сохранённые образцы. Командный запрос читает только сводки и проекции размеченных отрезков. Проекции лучших мощностей и размеченных отрезков хранить в существующем JSON метрик, с версией расчёта и ID источника. Для старых файлов считать отсутствующие проекции на сервере ограниченными порциями при обработке детали или по отдельной команде на тестовой копии. Валидация и запись проекции проверяют актуальность источника и разметки. Сводка отмечает ожидающие обработки источники как неполные.

### Взаимосвязи и достаточность

- На дату начала эпизода приходится первое превышение дневной нормы или переход недельной нагрузки через порог. Близкие нагрузочные эпизоды с пересекающимися семидневными окнами реакции объединяем в один эпизод. Даты ключевых тренировок сохраняем. Каждая реакция относится к одному эпизоду и выводится на временной шкале один раз. Для каждого события показываем даты и задержку до ближайшего предшествующего дня повышенной нагрузки в пределах эпизода и семи суток. Группы задержек — 0, 1, 2, 3, 4–7 суток. Незакрытые окна помечаем. Анкета за тот же день может быть заполнена до тренировки, поэтому её показываем как совпадение по дате.
- Для статистики брать дневное отклонение TSS и отклонение наблюдаемого показателя от его нормы. Считать ранговую корреляцию Спирмена отдельно для каждого спортсмена, показателя и задержки 0…7 дней. Использовать только известные пары `d → d+k` с одной парой на исходную дату для данного показателя и задержки. Окно статистики — 180 дней. Начальный минимум — 30 пар, минимум 12 пар в каждой хронологической половине, ненулевая вариативность и совпадение знака в обеих половинах для отметки об устойчивости. Показывать коэффициент, размер и период выборки, отдельно указывать, что соседние даты могут зависеть друг от друга. Для малой выборки показывать только датированное описание. Коэффициент не используется как самостоятельное условие предупреждения.
- Статусы по каждому направлению и показателю: «Достаточно», «Частично достаточно», «Недостаточно», «Показатель не поддерживается», «Данные отсутствуют». API возвращает причины, число наблюдений и покрытие. Частично известную сумму показываем как сумму записанных TSS с количеством тренировок без TSS. Возможные дубликаты блокируют численные сравнения затронутых периодов до появления однозначных данных. Отсутствие предупреждения само по себе не подтверждает хорошее восстановление.

## Правила и объяснения

| Код | Стартовое правило | Приоритет просмотра |
| --- | --- | --- |
| A | Недельная нагрузка ≥20% выше собственной нормы и есть устойчивое ухудшение восстановления в эпизоде. | Умеренный. Высокий при полном подтверждённом покрытии нагрузки и ≥3 днях с несколькими ухудшившимися показателями. |
| B | Недельная нагрузка выросла ≥15% от предыдущей сопоставимой недели, а в конце периода появилось или усилилось устойчивое ухудшение восстановления. | Умеренный. При одновременном A в карточке эпизода видны оба условия и общие доказательства. |
| C | Повторное снижение результатов размеченного протокола по критериям сопоставимости. | Умеренный. Временное соседство с нагрузкой показывается при наличии наблюдений. |
| D | При полном подтверждённом покрытии недельная нагрузка ≥20% выше нормы, есть повторное улучшение размеченного протокола, а минимум четыре оценённых дня за неделю покрывают ≥2 группы восстановления без устойчивого ухудшения. При частичном покрытии показываем измеренные изменения в сводке. | Информационный. |
| E | Для связи нагрузки и восстановления не хватает сопоставимой истории, либо за предыдущие 14 завершённых дней дневник заполнен меньше семи раз. | Информационный. Показать числитель, знаменатель, недостающие даты и конкретный пробел. |
| F | После датированного нагрузочного блока с ухудшением есть измеренный возврат ранее изменившихся показателей к норме. | Информационный. |

У предупреждения есть стабильный идентификатор эпизода, название, приоритет, период, достаточность и факты с полями «значение», «норма», «отклонение», «единица», «объём выборки», «дата» и ID тренировки, где применимо. Шаблон объяснения использует эти поля. Суммы и пороги сравниваем до округления. Предупреждения A–F вычисляются из данных и не требуют хранения истории уведомлений. Сортировка команды по максимальному приоритету активного предупреждения, затем по имени. Приоритет предназначен для очередности просмотра тренером.

### Контрольные сценарии

- Высокая нагрузка с ухудшением и при стабильном восстановлении, нормальная нагрузка с плохим сном, ухудшение и улучшение повторных контрольных усилий при росте нагрузки, измеренный возврат после блока.
- Неполный дневник, короткая история, отсутствие мощности и FTP, истинный нулевой RPE, неизвестный день и подтверждённый отдых, изменение покрытия, запрет вывода о норме при отсутствии данных.
- Одинаковая недельная нагрузка при двух индивидуальных нормах, перекрывающиеся блоки с одной реакцией, контрольные задержки 0…7 суток, разрешённые и недостаточные выборки для корреляции.
- Исторический FTP после обновления профиля, повторный FIT и обновление источника, потенциальный дубликат, границы суток для разных IANA-поясов и переход на летнее время.
- Гость, тренер и два спортсмена. Доказательства и числа в API и интерфейсе проверяются на синтетических данных, в том числе контроль `680 / 510 − 1 = 33,33…%`.
